# 平假名注音架构与算法

2026-10-11：本文描述“整句来源对齐 v2”，替代原有相似度筛选、逐词贪心匹配和失败后词典覆盖流程。

关联：[格式与排版](FURIGANA_SPEC.md)、[案例与陷阱](FURIGANA_CASEBOOK.md)。通过对齐表示来源与正文满足当前规则，不代表来源资料自身或全部游戏画面已经人工确认。

## 1. 数据流与责任

```text
最终时间线 JSON / SRT
  → 同来源、同 lyric ID、同日文全文选择 lyric_en
  → 正文脚本单元 + 固定假名约束 + 来源罗马音
  → 完整消费来源的最优切分图
  → 确定的汉字跨度 / 歧义记录
  → Ruby TSV + 审计 JSON + 可读 Markdown
  → 三件套哈希保护安装
  → DLL 按有效歌词行号绘制
```

- `scripts/furigana_alignment.py`：严格罗马音转换、固定假名模式、有界动态规划和来源证据。
- `scripts/generate_furigana_sidecar.py`：来源配对、Janome 参考、有效行号、TSV/审计；新旧入口共用同一个逐行方法。
- `scripts/extract_native_lyric_timeline.py`：原生事件与连续重复归并。
- `scripts/export_lyrics.py`：成套生成、快照发布、安装所有权与哈希保护。
- `scripts/export_ruby_review.py`：选择 PV 或全部导出，正文插入注音，同时显示来源与复核原因。
- `scripts/review_furigana_alignment.py`：全量跨度、行号、哈希、完整消费检查，新旧读音差异和待复核清单。

游戏 DLL 不运行分词或推导读音；现有签名、Hook、加载生命周期不参与本次算法修改。

## 2. 来源优先与词典边界

来源表必须匹配 lyric ID 和日文全文。`lyric_en` 名称不能证明内容是罗马音：英文翻译也可能出现在该栏。删除原来的 60% 相似度放行规则，以实际完整对齐决定是否可以使用。

正文固定假名先约束来源消费；汉字读音来自其对应的来源片段。词典提供助词词性与同音边界参考：只有候选发音与词典相同，才可用其切分证据或等价长音拼写。词典不能把来源 `kimi` 改成 `くん`，不能把来源 `hitori` 改成 `いちにん`。

**来源存在但不能完整对齐时，不回退发布词典注音。** 来源缺失时才保留明确标记为“词典推测”的参考注音，审计提示尚未核对歌曲唱法。这类输出不属于已确认读音。

来源同 ID/正文匹配、固定假名、罗马音转写和词典同音边界均是可检查约束，并不是语言学唯一性证明；纯汉字的特殊唱法仍依赖来源资料准确性。

## 3. 正文单元与严格消费

按原文 Unicode 位置划分连续汉字组、平假名、片假名、英文、数字、空白、标点。汉字范围包括 `々/〆`。不能对改变长度的规范化文本计算 span。

- 假名消费有限转写变体；支持促音、长音、助词 `は/wa`、`へ/e`、`を/o/wo`，以及 `しぇ/she` 等外来音。
- 送り假名是正文固定约束，例如 `近づく` 的 `づく` 自己消费 `zuku`，只有 `近` 获得 `ちか`。
- 数字保留实际发音消费，但不重复输出汉字 Ruby。`38度5分` 来源 `sanjuuhachi do gobu`，故 `分` 是 `ぶ`。
- 英文正文直接消费相同英文；片假名外来语采用有限、明确的源词读法映射，且映射结果必须完整匹配该片假名单元。未知大写词不能当成任意片假名占位；已知英文词不能被汉字当作日语罗马音解析。
- 明示 `才能（ちから）` 时，括号读音作为对应汉字约束，只唱一次；不把括号假名重复推进来源。
- 空白与标点不发音，但保留边界证据。源词分隔只读取相邻词之间的原始分隔，避免把更早标点误认成当前边界。
- 罗马音必须全部解析；未知字母、未消费尾部、非 ASCII 读音文字均不能静默删除后当成成功。

## 4. 切分搜索、歧义与资源

状态为 `(正文单元序号, 来源游标)`。终态要求所有正文单元结束且来源全部消费。优先满足正文/来源分隔，再以词典同音证据辅助切点；不会按词典默认读音改写来源。

每个状态保存最优代价和最优边。最后从根遍历最优切分图，汇总各汉字组所有候选读音；不同候选读音无法确定时，不输出该组 Ruby，其他确定组仍可输出。完整原文、候选消费范围、来源片段、来源依据、词典参考和明示读音保存在审计中。

重复同字只有在对应来源读音能等分成相同片段时才逐字标注。例如五个 `恋` 对五个 `koi`，产生五个单字 `こい`；不按 PV 编号写补丁。

资源上限：来源长度 800、正文单元 200、搜索状态 40000、每次外来语别名序列候选 512。搜索超限整行拒绝猜读。路径保存由复制整条路径改为切分图；逐行搜索缓存显式清理，跨行缓存限制为 256，防止全量导出累计保留过多数据。超过上限不保证注音覆盖，应按审计处理。

## 5. 行号、末句与重复事件

TSV 第一列从 1 起，为运行时保留的非空且时间有效歌词序号。审计同时保存物理 `index`、有效 `runtime_index`、原始 `lyric_id`；三者不能互换。TSV 与审计有效索引必须完全一致，重复 TSV 行号直接拒绝。

SRT 末尾保留空白分隔，确保现有 SubRipParser 接纳最后一个 cue。连续相邻同 ID、同正文，间隔 -100 至 250 ms 时归并，起点保留前段、终点保留后段；不限制前段长度。明显空档、不同 ID、不同正文不按文字去重。

span 偏移按 Unicode 字符，不是 UTF-8 字节。现有 309 首正文未发现非 BMP 字符；若以后引入非 BMP 字符，应单独核对 Windows 运行时的 UTF-16 索引，不把当前检查外推到新字符集。

## 6. 验证与维护

| 证据 | 能证明 | 不能证明 |
| --- | --- | --- |
| 完整对齐 | 正文固定读法和来源在当前规则下可对应，来源无残余 | 来源唱法本身无误，所有切点语言学唯一 |
| 回归 | 所列典型句、拒绝猜读条件、入口一致性正确 | 未列句全部读音正确 |
| 全量审计 | 309 首行号、跨度、哈希、来源消费和提示一致 | 无提示即人工审核通过 |
| 真实 parser | 有效行数和最后一句实际可被加载 | 游戏画面与听感正确 |
| 安装核验 | 本次文件与安装文件 SHA-256 一致 | 当前已运行游戏加载了新版 |

维护时先加入原文、来源、预期 span 与失败条件回归，再全量比较变化。人工修改文件受所有权哈希保护。无法对齐的资料应修正来源或添加有证据的通用转写规则，不能事后偷偷改 TSV 来伪装算法成功。标记分别使用 LOGIC VERIFIED、DEPLOYMENT VERIFIED、IN-GAME VERIFICATION REQUIRED。
