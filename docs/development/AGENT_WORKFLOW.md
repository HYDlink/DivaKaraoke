# 开发与文档约定

先读[构建说明](../BUILD.md)，配置自己的 `.local/environment.toml`。开发助手还应读取可选的 `.local/agent-notes.md`。实际目录和临时上下文不写入公共文档。

## 一次改动的流程

1. 确认要改变的行为和最小范围。
2. 涉及外部行为时更新对应[规格](../specs/README.md)；实现方法与持久取舍分别进入架构和决策。
3. 完成适当验证，记录能证明什么、尚未证明什么。
4. 用户操作发生变化时更新对应指南；用户指南不承接排错过程。
5. 更新 STATUS 和 PLAN 的当前摘要，详细日志留本地报告或有明确范围的变更记录。

## 文档放哪里

| 内容 | 位置 |
| --- | --- |
| 安装、操作、常见问题 | README 与 docs 用户指南 |
| 当前行为约束 | docs/specs |
| 系统结构与持久决策 | ARCHITECTURE / DECISIONS |
| 本次任务当前进度 | 精简的 STATUS / PLAN / CURRENT_HANDOFF |
| 个人目录、缓存来源、助手本地笔记 | 忽略的 .local 目录 |
| 原始日志、截图对比、逐曲审计 | 本地报告或 artifacts |
| 有追溯价值的旧研究 | 明确标注的 docs/archive，按需阅读 |

禁止往用户指南追加“本轮修复”“本机部署”“某日验收”等流水。不要用过去的一次成功记录替代当前安装方法。变更说明只写用户能感知的行为和真实限制。

新方法写中文注释，源码使用 UTF-8，日常工具输出中文。游戏签名、结构体偏移及 Hook 变更需要明确证据；文档整理不构成修改游戏集成层的理由。

当前未强制采用 OpenSpec。将来如果引入，当前规格映射到 specs，具体变更单独建 proposal/design/tasks；用户指南和设备配置仍保持独立。不要为安装一套流程工具重复堆出另一批同义文档。

旧诊断和部署脚本保留供源码追溯，部分需要专门测试输入，不作为日常用户入口。需要重新使用时，先接入自己的本地配置并验证，不能照搬历史默认目录。
