# 逐字歌词离线生成与运行时实施方案

日期：2026-10-25。状态：方案已明确，生产生成器、字级加载器和渲染尚未实现。当前依据为[PV045可行性证据](research/pv045-character-timing-feasibility.md)。用户确认以现有完整SRT为正文与行级基础，不依赖LLM逐句填写时间。

## 一、交付目标与数据职责

最终日常流程：用户运行现有歌词导出入口，脚本从已提取资产自动生成并校验整套歌词文件，Mod加载后按每个字/音节的独立时间填色。研发中的抽样听辨/逐帧评测用于衡量算法误差，不是日常每首歌、每个字都由人工或LLM制作。

| 层 | 权威输入/产物 | 职责 |
| --- | --- | --- |
| 行级 | 现有`PVnnn.srt` | 完整正文、行显示窗口、下一句预告、轨道、段落及整体淡出。 |
| 行级身份 | 现有`PVnnn.singers.tsv` | 本行歌手身份与合唱配色，沿用现有人工修订。 |
| 字级/发音级 | 新增`PVnnn.timing.tsv` | 正文单字/可信词组、假名读音单元各自的开始/结束、填唱进度段。 |
| 注音 | 现有`PVnnn.ruby.tsv` | 汉字组与显示读音；字级时间引用同一份Ruby几何。 |
| 离线证据 | 新增`PVnnn.timing.audit.json` | 原始口型、读音消费范围、分支/槽位、匹配候选、时间依据、拒绝原因和输入哈希。 |

行显示起止与演唱起止是两个概念。SRT可提前显示、在尾音之后保留；不要求最后一个字恰好唱到SRT结束。歌手标记与填唱时间也不互相覆盖：字级对齐失败不会清除行歌手，不用新算法偷偷重判现有声部。

正文、假名与动画事件之间需要显式映射。例如「頭」占一个正文字形，但读音有「あ・た・ま」三个推进段；「きゃ」有两个假名字符而通常是一个发音单元。熟字训不能可靠拆到每个汉字时保留词组跨度，标为词组精度，不能叫作每个汉字边界都已恢复。

## 二、文件格式选择

**首版采用SRT加版本化时间旁路，不迁移现有歌词主文件。** 这是为现有运行时补齐缺少的时间层；不把一个字拆成一个SRT cue。

[美国国会图书馆的SRT格式说明](https://www.loc.gov/preservation/digital/formats/fdd/fdd000569.shtml)描述的是每个cue的起止和正文，没有独立的行内音节时间字段。在正文插入自定义标记需要自己定义和实现解析，不能再当作标准SRT逐字能力；逐字拆cue还会改变当前行选择、预告与歌手绑定。

用户所称的高级LYC可按增强LRC的目标理解：一行内部还有时间标记。它可以在后续成为兼容导出项，但当前内部还需要保留正文/读音映射、明确终点、空档和证据状态，不将其设为唯一主文件。是否支持某一种增强LRC方言及其精度，应在兼容导出阶段固定并回读核验。

ASS也能表达音节扫色；[Aegisub官方文档](https://aegisub.org/docs/latest/ass_tags/#karaoke-effect)说明`\kf`按音节时长从左到右扫色，其时长以百分之一秒计。现有Mod已经有字体、描边、Ruby和合成渲染，不需要为逐字功能先引入ASS渲染器。首版运行时仍用现有ImGui/DX11。

时间旁路采用TSV，是因为当前歌手旁路已有严格流式读取范式；不为本功能另外引入JSON运行时依赖。复杂证据保存在离线JSON中，DLL只读取已完成的渲染数据。

## 三、时间精度与验收目标

必须分别报告以下精度，不用同一个“精确”概括：

| 项目 | 明确约定 |
| --- | --- |
| 原始事件分辨率 | DSC时间单位为十万分之一秒，即0.01ms；离线审计保留原始整数。 |
| 导出/加载分辨率 | 使用歌曲绝对时钟的整数毫秒，单位1ms；源整数在最后一步四舍五入到毫秒，不逐段累加时长。量化误差不超过0.5ms。 |
| 渲染更新频率 | 每帧读取既有游戏播放时钟直接求当前进度，不累计帧间时长；60FPS画面每约16.7ms更新一次，160FPS每约6.25ms更新一次，另有呈现/显示链路延迟。 |
| 实际对齐误差 | 目前未知；动画触发不是实际发声开始。首版研发目标是可辨识边界绝对误差P50≤50ms、P95≤100ms。该目标尚未达成，不是保证。 |
| 异常统计 | 开始、结束分别统计；除百分位外报告最大误差、超过100/200ms数量、未解边界比例及词组/字级覆盖率，不能只挑成功样本。 |

音频基准需记录采样率、原始采样位置、歌曲起点和所用版本。只有视频时，60FPS逐帧参考本身约有一帧的不确定范围，不能用它证明1ms听感准确。主观不易界定的渐入/连唱边界记录区间，不强制编造单一真值。

初始基准集限定《Dear》：首句、连续同元音、促音/拨音、停顿、长音和最后一句，目标至少100个可辨识的开始/结束边界；算法参数校准段与评测段分开。人工只建立一次研发评测集，日常生成不要求人工标歌。没有评测数据时，误差字段为未知，不能填“±50ms”或人为编造置信概率。

首个里程碑可以交付“口型推导的逐字预览”，但只有在误差与覆盖率有实测后，才能声称已达到对应的歌唱同步精度。首版不要求100%曲库覆盖。

## 四、离线流水线

```text
最终有效SRT + 同源时间线JSON + Ruby/读音审计 + 现有歌手标记
    → 完整行绑定与版本指纹
    → 正文/读音/发音单元映射
    → 生产DSC读取器收集带槽位、分支的口型事件
    → 已验证编号族的口型类别转换
    → 受正文顺序和行窗口约束的全局对齐
    → 起止时间候选、长音合并与空档判断
    → 精度/歧义/覆盖检查
    → timing.audit.json + timing.tsv + 中文摘要
    → 导出器成套发布/哈希保护安装
    → DLL加载预计算数据并逐字填色
```

### 第1步：以最终SRT为输入合同

先按实际生产parser的语义建立非空且时间有效的行序；零时长行可保留显示，但不生成正时长逐字段。SRT行号、原始lyric ID和运行时有效行号分别保存。确认缓存JSON与最终SRT的时间/全文一致；不一致时拒绝借用该曲旧口型映射。

读取当前有效来源，不凭PVID猜物理DSC或音频编号。换唱、Mod覆盖、同曲版本的指纹变化会使旧时间结果失效。手改SRT必须重新绑定；没有可匹配来源时正常输出行级歌词，并说明字级不可用。

### 第2步：建立完整发音单元，而非只抽a/i/u/e/o

从已存在的`ruby.audit.json`来源消费范围及`furigana_alignment.py`复用确定的正文—读音映射；正文固定假名也必须纳入，不能只读可见Ruby TSV。每个单元保留原文范围、读音范围、来源字符范围和发音类型。

普通元音、拗音、促音`っ`、拨音`ん`、长音、无声标点/空格分别表示。英文等没有可靠发音映射的片段显式拒绝，不靠LLM或词典默认读音猜完整唱法。当前已发现的整句缺注音问题需要共同的可靠读音层，但字级工程不把“TSV没有Ruby”一律当成整行没有已知读音；只消费审计中确实成立的片段，未知跨度明确保留。

读音模块可独立复用，不要求先把全曲库注音覆盖率修到100%。首版《Dear》先用已有确定映射验证接口，已知读音缺口计入未解覆盖。

### 第3步：收集并解释口型

调用已有`build_singer_timeline.read_commands`，保留事件原始时刻、命令偏移、角色槽、分支和过渡参数。不重写CPK/DSC parser，不在DLL读资产。

建立版本化编号族配置。官方24/25/31/32与另一套0/1/2/10/11等不能混用；`choose_activity_poses`用于行级歌手活动的频率扩展规则不能当作音素表。首版只接受经过《Dear》实证的官方编号族；跨PV推广前需独立样本/引擎或资产证据验证，不按每首歌临时猜一张映射表。未知姿态保留未知。

多个角色的事件不能简单拼接。先按角色槽/分支对齐，再以已有行歌手限制候选；同身份复制槽去重。成功/失败分支结论不同、两个人同一句唱不同内容、手工身份与事件冲突时记录为未解，不清掉原歌手颜色。首个实验只做单角色《Dear》。

### 第4步：用脚本做约束序列对齐

第一层使用确定性动态规划匹配已知读音类别与口型事件。允许匹配、未知/额外动作、缺事件、重复事件表示同一延音等候选转移；促音/拨音是独立状态，不强行变成一个元音。

保留所有同样最优的切点及与次优路径的分差。类别一致、时间顺序、分支一致、正文边界、跨句事件所有权均需满足。不能只取一条最优路径就称唯一，也不能只根据“元音数相等”判精确。

候选事件窗口以SRT及相邻行确定，允许检查行外少量事件，初始搜索外扩上限可设250ms并纳入版本配置；这只是搜索范围，绝非精度承诺或统一补偿。整首同槽的事件分配要单调，同一事件不得重复消费到连续两行，跨句所有权不唯一时保持未解。

同一字的长音有多个事件时可以在已有读音约束下合并成一个持续发音；多个字共用一个持续姿态时不能均分时间伪造字边界。算法代价与阈值按版本保存，校准集确定后冻结，再跑保留评测段。

现有`research_pv045_mouth.py`只是先导工具：能比较元音、保留编辑距离最优匹配及首句候选，**尚不是完整的自动逐字生成器**；不能把它的首句样例直接复制到生产冒充全自动完成。

### 第5步：求开始、结束与字间停顿

起点和终点分开推导。下一次元音命令只给出一个候选边界；基准姿态28、第四参数Transition、SRT行末都不能直接当作发声终点。禁止全曲统一减100ms，也不把未知终点默认填成下一字起点后标为实测。

先输出口型候选边界及依据。首句校准后，若能建立稳定、可复核的动画—发声关系，再形成版本化时间规则；如果长音/停顿或同元音丢边界无法靠口型消歧，进入**离线音频补证**：固定已知歌词与候选窗口，评估适合歌唱的强制对齐/音素证据，不让模型另写歌词。不能只用混音音量门限判断某个字，不能把伴奏节拍当人声边界。

音频补证不是目前已有能力；工具/模型选择、依赖、速度和歌唱长音精度在第二阶段单独小样验证。音频或分轨缺失、信号不可分或仍有多个同等候选时，保留未知。音频模型即使被采用，也在离线运行，日常不调用LLM，不进入游戏帧线程。

### 第6步：编译渲染用时间与几何映射

将已确定的发音段映射到正文单字/可信词组和Ruby读音。每段保存明确开始/结束，字间没有发声的时间不强制纳入前字。一个字的多个发音段使用进度子区间；例如「頭」三个音节可依次推进0→1/3→2/3→1。

这种分数分配描述字形内的可视推进，不代表汉字左1/3天然就是「あ」。若无法拆分复合词的正文边界，只生成词组段并明确精度。Ruby按实际显示的每个假名/拗音单元独立推进，不借用正文整行横坐标。

只要本行还有未确定的演唱字/终点，首版整行回退旧均匀填唱，避免一部分精确、一部分任意补时造成速度突跳。离线审计保留已经找到的局部锚点，供算法改进；后续若引入局部回退，必须另定显示规则。

## 五、时间旁路v1合同草案

编码UTF-8，所有时间为歌曲绝对整数毫秒，区间采用`[start_ms,end_ms)`。索引明确采用UTF-16码元，与现有Windows正文/Ruby几何入口一致；Python需显式转换，拒绝落在代理项对中间的范围。不能将Python字符下标或UTF-8字节直接写给DLL。组合字符/拗音等可用多码元SPAN表示，不把它们误当两个独立发声。

记录之间用TAB分隔，文本字段按统一规则转义反斜杠、TAB、CR、LF，先分列再反转义；不做会改变原文字长的隐式规范化。下表是协议草案，尚无生产读取器：

| 记录类型 | 字段 | 含义 |
| --- | --- | --- |
| `META` | 版本、PVID、有效行数、单位ms、索引utf16、SRT文件SHA-256、Ruby文件SHA-256 | 强绑定这一套被安装的文件。 |
| `LINE` | 行号、SRT开始、SRT结束、模式、完整正文 | 每行必有；模式为`timed`或`fallback`。 |
| `SPAN` | 行号、跨度ID、正文起点、正文长度、读音、粒度 | 正文单字/词组或发音簇，粒度`character/group/cluster`，不包含歌手重判。 |
| `STEP` | 行号、跨度ID、步骤号、开始、结束、起始分子、结束分子、分母、依据 | 一个正文跨度内的单调线性推进段；用整数分数避免浮点文本歧义。依据如`mouth_proxy/audio_refined`。 |
| `RUBY` | 行号、Ruby跨度序号、读音起点、读音长度、开始、结束、依据 | 绑定当前Ruby文本及几何中的独立读音单元。 |

`timed`行的全部演唱正文跨度必须覆盖、顺序一致，每个SPAN的STEP从0完整推进到1；STEP间可有空档，空档维持上一进度。无声空白/标点的视觉归属显式记录在离线审计和编译规则中，不制造发声时间。`fallback`行不得夹带部分启用的STEP。

本协议包含词组映射和正文/Ruby双时间层，功能超过简单的“每字一个起点”；未来可从相同结构导出增强LRC或ASS，并记录目标格式量化误差。导出格式不会提高原始时间准确度。

加载必须拒绝：不支持版本、PVID/哈希/全文/总行数不符、重复ID/遗漏LINE、越界索引、整数溢出、零/负时长、倒序/非法重叠、推进分数回退或超过1、Ruby文本不匹配。`timed`发音段应位于对应行显示窗口内；发现真实演唱越过SRT边界时先报告行绑定冲突，不静默截断或改SRT。

先解析到临时容器，整份结构有效才提交；文件损坏整份旁路回退，合法`fallback`记录只影响对应行。文件缺失不影响原SRT、Ruby或歌手功能。切歌/重播/返回菜单清空并重新绑定，与现有生命周期保持一致。

算法状态、匹配歧义、原始TIME整数、各候选边界范围、编号配置版本、音频/DSC/读音哈希、校准版本、未解原因和实测误差在audit中保存。`mouth_proxy`只说明依据；不是“±多少毫秒已经被验证”的标签。

## 六、运行时逐字填唱

在`LyricLine`增加独立的字级时间集合，行时间和`singers`继续原职责。计划新增`character_timing.h`用于强绑定加载、时间求值和范围校验；几何继续复用`ktv_geometry.h`，渲染接入`DrawKtvLine`、`DrawKtvWipeText`和`DrawKtvRubySpans`。

每帧以当前游戏时钟直接定位STEP，计算：

```text
段进度 = clamp((当前毫秒 - 段开始) / (段结束 - 段开始), 0, 1)
字内进度 = 起始分数 + (结束分数 - 起始分数) × 段进度
填色边界 = 当前正文跨度左侧 + 跨度实际宽度 × 字内进度
```

段间空档保持边界，长音在本字内慢走，段末正好到规定边界。单声部单调正文可继续用一条变速裁剪边界绘制整句，不逐字创建字体/纹理。Ruby使用其自身时间与几何，仍复用原配色、描边、阴影和整体透明合成。

字符边界、STEP检索表和Ruby几何在加载/字体/分辨率变化时缓存。帧内不分词、不跑动态规划、不读写文件、不进行音频推断或大量字符串分配。允许倒放/跳转/暂停恢复，不能靠上帧累计进度；歌手合唱颜色仍按当前行样式取色。

### 导出器具体接入点

- `scripts/export_lyrics.py`：最终SRT/Ruby/歌手生成完成后增加字级阶段，计划提供`--rebuild-timing-only`与显式PVID选择；这些参数现在尚不存在。
- `generate_ruby_cache`或`generate_singer_cache`发生依赖变化时，按SRT/Ruby/来源/算法指纹重建或失效字级文件；不能保留旧哈希下的timing。
- `manifest_files`与`install`目前只接纳固定SRT/Ruby/歌手文件集合，需一同扩展`.timing.tsv`及`.timing.audit.json`，安装manifest计划升级v4并兼容旧v1–v3所有权。
- 默认正式导出是否对所有有效曲启用字级阶段，在C7验证后再切换；首版不自动全库扫描。
- 证据生成失败要与普通“不支持/未解”区分：前者阻止发布错误结果，后者发布合法回退状态；同套文件先校验再原子发布，安装仍保护用户文件。

### 日常使用终态

用户只需运行原导出入口或后续“仅重建逐字时间”的短入口，无需安装额外在线服务、打开LLM逐字标歌、手改每首时间。工具中文摘要列出字级/词组级成功行、回退行、原因、运行耗时及精度依据；审计可追溯到原始事件。
